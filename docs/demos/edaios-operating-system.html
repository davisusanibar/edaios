CRECIMIENTO GOBERNADOSIN INICIATIVA INSTALADA

La siguiente iniciativa entra por contrato

Core solo crece cuando una necesidad real aporta owner, fuente, manifest, spec, decisión estructural cuando aplica y evidencia proporcional.

  • Partir de una necesidad y un owner reales
  • Crear un attachment con namespace, autoridad y sensibilidad
  • Abrir una feature Spec Kit con requisitos y criterios observables
  • Aceptar por ADR cualquier nueva frontera estructural
  • Ejecutar initiative-adoption antes de materializar el consumer
LÍMITE
Templates y adapters conservan forma, no instancias. El adapter Engram está incluido, pineado, probado y es degradable; el runtime Engram no está instalado. Tampoco existe dominio, engine, producto, connector, dataset ni consumer instalado.

QUÉ HEREDAS Y QUÉ CREAS

Qué heredas, qué consumes y qué creas

HEREDA Constitución compilada

Cuándo: Siempre. Se cambia en su fuente gobernada y se recompila; nunca se enmienda dentro de una feature.

Persona: Cita la Constitución y documenta PASS, N/A o VIOLA para los principios I–VII.

Sistema: FND-PROJECTION comprueba que la vista coincide con Foundation; Spec Kit detecta un pin obsoleto.

Evidencia: Constitution Check trazable y huella vigente en plan.md.

NO: Editar la proyección compilada, ocultar VIOLA o relajar una regla dentro de la feature.

HEREDA KOM + gates de validación

Cuándo: Siempre. Se ejecutan; no se duplican, desactivan ni debilitan para una entrega.

Persona: Corrige la fuente cuando una puerta falla y vuelve a ejecutar el mismo contrato.

Sistema: KOM, validadores y scripts operan fail-closed sobre identidad, estructura, enlaces y promoción.

Evidencia: Comandos, versión, resultados y digest ligados al cambio.

NO: Copiar esquemas, editar reportes, silenciar fallos o declarar verde desde una conversación.

CONSUME Dominio y verdad del owner

Cuándo: Solo cuando existe input verificable y firma humana; el baseline T0 no precarga semántica institucional.

Persona: El owner aporta o acepta la verdad; el equipo mantiene explícito lo que todavía no se sabe.

Sistema: El template de dominio valida procedencia, ownership, sensibilidad y promoción sin valores TBD.

Evidencia: Intake y contrato de dominio con fuente, estado, firma y fecha.

NO: Inferir hechos, inventar owners o fuentes, copiar semántica de una instancia anterior o promover TBD.

CREA Spec Kit feature

Cuándo: Para todo cambio gobernado: convierte demanda en requisitos, plan, tareas y evidencia.

Persona: Especifica, aclara, aprueba checklist/plan/tareas e implementa solo después de analyze en verde.

Sistema: SDD-CONTRACT verifica identidad, fases, cobertura, Constitución y tareas de cierre.

Evidencia: Cadena requisito → tarea → cambio → prueba/gate → resultado.

NO: Empezar por código, saltar aprobación o marcar implemented con tareas abiertas o gates rojos.

A VECES RFC

Cuándo: Cuando el diseño está abierto y varias alternativas necesitan discusión y alineación.

Persona: Autores y revisores comparan opciones y registran objeciones; el owner no delega la decisión al documento.

Sistema: El ledger preserva el borrador y su estado; ningún gate transforma comentarios en autoridad.

Evidencia: Convergencia, rechazo o recomendación trazable que puede alimentar un ADR.

NO: Tratar el RFC como decisión vinculante, usarlo para trabajo rutinario o implementar antes de decidir.

A VECES ADR

Cuándo: Cuando se toma una decisión arquitectónica o de gobierno; puede nacer sin RFC si la elección ya es clara.

Persona: Registra Propuesto; el owner competente lo lleva a Aceptado o un ADR posterior lo deja Derogado.

Sistema: El ledger valida id, catálogo, estados y referencias, pero nunca ratifica por sí mismo.

Evidencia: Registro estable enlazado a fuentes, feature, materialización, revisión y consecuencias.

NO: Usarlo para explorar, escribirlo a posteriori para justificar código o marcar Aceptado sin revisión humana.

CONSTITUCIÓN

Siete principios que condicionan cada cambio

La feature los hereda; no los reescribe para hacer pasar una solución.

I

El conocimiento manda

Ninguna implementación tiene mayor autoridad que el conocimiento que la originó.

Lectura T0: Toda pieza retenida declara su spec, ADR, contrato o registro de origen.
Verifica: Trazabilidad resoluble desde intención hasta evidencia.
II

Spec antes que artefacto

Ningún artefacto gobernado se crea o cambia sin contrato previo.

Lectura T0: La feature nace tipada, se aclara y se analiza antes de implementar.
Verifica: artifact_spec_check y spec_kit_gate.
III

El canon crece por ADR

Ningún cambio estructural ocurre sin ADR.

Lectura T0: Una decisión estructural usa los estados exactos Propuesto, Aceptado y Derogado.
Verifica: Catálogo único, referencias resolubles y ratificación del owner de la capa.
IV

Cero cifras sin fuente

Todo número o claim cuantitativo conserva fuente, fecha y alcance.

Lectura T0: Los conteos del baseline provienen de catálogos; cualquier target futuro se rotula por su estado real.
Verifica: Registro de fuentes y revisión de claims.
V

Una fuente, muchas vistas

Git conserva la verdad; las demos, portales y diagramas son proyecciones regenerables.

Lectura T0: Esta vista se genera desde este JSON; no se corrige el derivado como autoridad.
Verifica: Generación determinista y diff limpio.
VI

La IA consume, el humano firma

La IA prepara, relaciona y verifica; no inventa la fuente de verdad ni acepta decisiones.

Lectura T0: El Principal Architect conserva el checkpoint estructural y cada owner conserva la verdad que aporta.
Verifica: Intent verbatim, owner explícito y evidencia de aprobación.
VII

Privacidad por diseño

La sensibilidad se clasifica antes de cualquier ruta de consumo o IA.

Lectura T0: N/A para el baseline vacío: T0 no procesa PII, secretos, credenciales ni datasets. Todo dominio futuro deberá activarlo antes de consumir datos.
Verifica: Clasificación, fuente, owner y gate del dominio antes de promoción.

OCHO FASES

Spec Kit: ocho fases, un contrato

Spec Kit orquesta; la Constitución y los gates EDAIOS deciden.

01 · HEREDA Y VERIFICA

Constitution

Entrada: Fuentes Foundation y proyección compilada.

Salida: Versión y SHA-256 vigentes; principios I–VII disponibles para el plan.

Bloquea: Una proyección derivada o un pin obsoleto bloquea el plan.
02 · DEFINE

Specify

Entrada: Intent, owner, valor, fuentes, sensibilidad y alcance.

Salida: feature.spec.yaml + spec.md con FR y SC.

Bloquea: No se diseña implementación sin contrato tipado.
03 · DESAMBIGUA

Clarify

Entrada: Spec y decisiones abiertas de alcance, riesgo, privacidad o valor.

Salida: Aclaraciones integradas y preguntas resueltas.

Bloquea: Una ambigüedad bloqueante impide planificar.
04 · EVALÚA

Checklist

Entrada: Spec aclarada.

Salida: checklists/requirements.md evaluado, no solo enumerado.

Bloquea: Un ítem crítico pendiente impide el plan.
05 · DECIDE CÓMO

Plan

Entrada: Constitución, spec, checklist y ADR/RFC citados.

Salida: plan.md con alternativas, decisión, estructura, pruebas, reversa, Constitution Check y Gate Impact.

Bloquea: VIOLA detiene el plan; el camino de excepción es un ADR.
06 · ORDENA

Tasks

Entrada: Plan aprobado y requisitos.

Salida: tasks.md con dependencias, cobertura FR y cierres GATES/LEDGER/INGEST/SEAL cuando aplican.

Bloquea: No se implementa con requisitos sin tarea o tareas huérfanas.
07 · PRUEBA COHERENCIA

Analyze

Entrada: Spec, contrato, checklist, plan y tareas.

Salida: Informe de solo lectura sobre cobertura, duplicidad y conflictos de gobierno.

Bloquea: Cualquier CRITICAL, HIGH o gate rojo bloquea implement.
08 · MATERIALIZA

Implement

Entrada: Plan y tareas aprobados con analyze en verde.

Salida: Diff, pruebas, gates y evidencia de cierre.

Bloquea: Solo se marca implemented con todas las tareas completas y gates verdes; commit/push requieren autorización explícita.
